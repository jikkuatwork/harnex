harnex

Pi workers as tools for you and your coding agents.

Hand a question or a task to a Pi worker (a GPT model by default) and get the reply back in one call: in its own git worktree, in a tmux window you can watch, with follow-ups that keep the worker's context. From your shell, or as native tools in Claude Code and Pi.

$harnex mcp installclaude code + pi

the verbs · harnex --help

Seven commands. Plain text in, plain text out.

Every command blocks until the worker replies, then prints the reply and a footer with the state, model, cost, commits and the next commands. Exit 0 done, 1 failed, 124 still working.

ask "QUESTION"
A second opinion. The worker reads the repository and answers; it changes nothing.
delegate "TASK"
A worker does the task. Add --worktree NAME to give it its own git worktree.
result [NAME…]
Collect parallel lanes. Prints each result as it lands.
reply NAME "…"
Follow up. The worker keeps its context, even after it finished.
land [NAME…]
Merge a worktree lane. Then removes the worktree and the branch.
discard NAME
Drop a lane. Stops the worker, deletes its worktree and branch.
lanes
What is open. And what each worker is doing right now.

three ways in

Built to be driven by agents.

A supervising agent hands work to a Pi worker, keeps going, and acts on the reply. The same verbs work from a shell, as MCP tools, or through a Claude Code subagent.

Your shell · any agent

Run several workers at once, each in its own worktree, then land them.

$ harnex delegate --no-wait \
    --worktree a "Task A"
$ harnex delegate --no-wait \
    --worktree b "Task B"
$ harnex result
$ harnex land

Claude Code · MCP

Native tools. A long call moves to the background on its own; Claude is notified when the worker finishes.

Pi · MCP or CLI

Pi supervises Pi. Tools are declared like built-ins; workers can never start more workers.

# ~/.pi/agent/mcp.json
"harnex": {
  "command": ".../harnex",
  "args": ["mcp"],
  "exposure": "direct"
}

anatomy of a lane

Every result says what happened and what to do next.

footerharnex 0.29
── word-count: done in 49s · gpt-5.1 · $0.03 · 1 commit, 2 files (+12 -0)
   worktree .harnex/worktrees/word-count (branch harnex/word-count)
   next: review `git diff HEAD...harnex/word-count`,
         then `harnex land word-count`;
         more work: `harnex reply word-count "..."`

── slow-bench: still working (9m02s so far)
   keep waiting: harnex result slow-bench

── fix-a: FAILED after 3s (model_not_found) · gpt-9
   next: harnex reply fix-a "Continue the same task
         from where you stopped" --model openai/gpt-5.1
  1. A name. The lane's name is its tmux window, its branch (harnex/NAME) and the handle for every later command.
  2. State, time, model, cost. Read from the worker's own usage report, summed over every turn.
  3. What changed. Commits and a diffstat since the lane started, straight from git.
  4. The next command. Land it, follow up, keep waiting, or retry on another model. The task is never lost: a retry resumes the worker's session.

underneath

A local harness for any terminal agent.

Lanes are ordinary harnex sessions. Pi runs in structured RPC mode, so harnex sees every turn settle and every command exit; Claude Code, OpenCode or any other CLI runs under a PTY. Each session gets a local control API, an event stream, a receipt of what it actually did, and a row in the dispatch history. run, send, wait, watch, pane and events stay available for custom orchestration.
